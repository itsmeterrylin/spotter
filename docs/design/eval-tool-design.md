# Spotter: system design

**Status**: Draft, 2026-09-06
**Scope**: A local, single-user tool for running and comparing LLM evaluations, with a human review loop and calibrated LLM judges.

## Goal

Run a test set through an LLM task, score every result, compare two runs by test case, and keep humans in the loop until the automated judge agrees with them.

## Principles

1. **The server never runs the task.** The SDK runs the task and the scorers and posts results. The server stores, aggregates, and compares.
2. **Binary verdicts.** A score is a name and a number. Human review is Pass or Fail with a note. No 1 to 5 scales.
3. **Error analysis before judges.** Read traces, write notes, group notes into failure modes, then write one judge per failure mode.
4. **Judges are validated, not trusted.** Every LLM judge is measured against human labels before its output counts.
5. **One process, one file.** SQLite and a single Bun process serving pages, REST, and MCP. Docker is for distribution, not a requirement.
6. **Judges are versioned, never edited.** Any change to a judge's prompt, model, or parameters creates a new immutable version. One version is active. Rollback is activating an older one.

## Data model

Twelve tables. A trace with a `run_id` is an experiment result. A trace without one is a production log.

| Table | Columns |
|---|---|
| `project` | `id`, `name` |
| `dataset` | `id`, `project_id`, `name`, `description`, `purpose` (`eval`, `judge_labels`) |
| `dataset_item` | `id` (client-set), `dataset_id`, `input` JSON, `expected` JSON, `metadata` JSON, `tags`, `source_trace_id` nullable, `archived_at` nullable |
| `run` | `id`, `dataset_id`, `name`, `metadata` JSON (model, prompt version, git sha), `item_count`, `items_hash`, `started_at`, `ended_at` |
| `trace` | `id` (client-set), `project_id`, `run_id` nullable, `dataset_item_id` nullable, `input`, `output`, `expected`, `metadata`, `tags`, `start`, `end`, `metrics` JSON (`prompt_tokens`, `completion_tokens`, `duration_ms`, `errors`), `messages` JSON nullable (transcript, `{turn, role, content, metadata}`), `events` JSON nullable (timeline, `{at, name, data}`), `spans` JSON nullable |
| `score` | `id`, `trace_id`, `name`, `turn` INTEGER nullable (null = whole transcript), `value` REAL, `label` nullable, `reason` nullable, `source` (`sdk`, `judge`, `human`), `judge_version_id` nullable |
| `judge` | `name` PK, `active_version_id`, `description` |
| `judge_version` | `id`, `judge_name`, `number`, `parent_id` nullable, `scope` (`turn`, `transcript`), `prompt`, `model`, `params` JSON, `examples` JSON, `content_hash` UNIQUE per judge, `created_by` (`human`, `agent`), `note`, `created_at` |
| `judge_calibration` | `judge_version_id`, `dataset_id` nullable, `split` (`dev`, `test`), `n`, `tpr`, `tnr`, `created_at` |
| `attribute_map` | `project_id`, `source` (attribute or event name), `target` (metadata key), `type` (`string`, `number`, `boolean`) |
| `alert_rule` | `id`, `project_id`, `name`, `enabled`, `trigger`, `condition` JSON, `channel` JSON, `cooldown_s`, `last_fired_at` |
| `alert_delivery` | `id`, `rule_id`, `payload` JSON, `status`, `response`, `created_at` |

Relationship chain:

```
dataset ──< dataset_item ──< trace >── run
                                │
                              score
```

Run aggregates (mean per score name, p50 duration, tokens) are computed on read, never stored. Turn scores roll up to the trace as the mean per score name; the trace-level score, when present, wins.

Ids are UUIDv7, generated by the client, so scores can be written before the server acknowledges the trace.

## API

| Method | Path | Purpose |
|---|---|---|
| POST | `/datasets` | Create dataset |
| PUT | `/datasets/{id}/items` | Upsert items by client id |
| POST | `/runs` | Create run |
| POST | `/traces/batch` | Insert traces; rows may carry `run_id`, `dataset_item_id`, `scores[]` |
| PUT | `/traces/{id}/scores` | Add or replace scores on a trace |
| GET | `/runs/{id}` | Run with aggregates |
| GET | `/runs/{id}/summary?compare_to=` | Per score name: mean, diff, improvements, regressions |
| GET | `/datasets/{id}/compare?run_ids=` | Items with nested per-run output and scores |
| GET | `/traces?filters=` | Filter grammar `[{field, key, operator, value}]` with symbol operators |
| POST | `/query` | Read-only SQL over the tables |

Filter operators: `=`, `!=`, `<`, `<=`, `>`, `>=`, `contains`, `starts_with`, `in`, `is_empty`.

## SDK and CLI

```ts
import { defineEval } from '@spotter/evals'

export default defineEval({
  dataset: 'tagging-golden',
  metadata: { model: 'rules-v1' },
  task: async (item) => tagTranscript(item.input.transcript),
  scores: [(item, output) => ({ name: 'exercise_match', value: output.exercise === item.expected.exercise ? 1 : 0 })],
})
```

```
spotter run evals/tagging.ts              # runs, posts, prints the summary table
spotter run evals/tagging.ts --no-send    # prints only
spotter compare <run_a> <run_b>           # summary with diffs
```

The summary table shows each score name with mean, diff versus the previous run, improvements, and regressions.

## Review interface

One screen, one trace at a time.

- Input, output, and expected in their native format. Markdown rendered, JSON collapsible, transcripts as transcripts.
- Pass, Fail, Defer as large buttons. Keys `1`, `2`, `D`. Undo with `U`.
- One notes field. Auto-save on every action.
- Counter: position, remaining, labeled.
- Failure tags appear only after error analysis has produced a taxonomy.
- Traces are loaded from a sample file. Sampling stays outside the app.

## Judge validation

1. Collect about 100 human labels per failure mode, balanced between Pass and Fail.
2. Split 15% train (few-shot examples), 45% dev, 40% test.
3. Measure true positive rate and true negative rate on dev. Iterate the prompt until both exceed 90%.
4. Run once on test. Record TPR and TNR with the judge version.
5. Report production pass rates corrected for judge error, with a bootstrapped confidence interval.

A judge whose TPR or TNR is unknown shows as `pending` in the UI and its scores do not enter run aggregates.

## Conversations: scoring by turn or transcript

A conversation is one trace whose `messages` array is the transcript. `input` is the first user message and `output` is the final assistant message, so single-turn code keeps working.

- A score with `turn` set applies to that turn. A score with `turn` null applies to the whole transcript.
- A judge version has a `scope`. A `turn` judge is called once per assistant turn with the transcript up to that turn and writes one score per turn. A `transcript` judge is called once with the full transcript and writes one score.
- Human review shows the transcript with a verdict row under each assistant turn and one for the whole conversation. Arrow down moves between turns; `1`, `2`, `D` apply to the focused row.
- Run aggregates use trace-level scores when present, otherwise the mean of turn scores per name. Compare shows the trace-level value and expands to turns on click.
- Deep link `/traces/{id}?turn=3` opens the trace scrolled to turn 3 with that verdict row focused.

## Extra inputs on a trace

Anything a system knows about a call can be attached to its trace, without a schema change, in three layers.

| Layer | Where | How it gets there | Example |
|---|---|---|---|
| Raw | `metadata.attributes`, `events[]` | Every OTel span attribute is kept under its original key. Every span event becomes an entry in `events` with its timestamp. | `lk.transfer.destination = "+1..."`, event `transfer_initiated` at 42.1 s |
| Promoted | `metadata.<key>` | The project's `attribute_map` copies chosen attributes or event names to top-level metadata keys with a type, so they filter, sort, and show in tables. | `lk.transfer.destination` → `metadata.transfer_to` |
| Late facts | `metadata`, `events` | `PATCH /traces/{id}/metadata` deep-merges data that arrives after the trace, from a webhook, a cron job, or an agent. | Telephony provider confirms the transfer completed |

Filters accept `metadata.<key>` and `events.name`. Judges receive the full trace, so a prompt can reference promoted fields by name. Nothing about voice, transfers, or any one framework is hard-coded; the attribute map is data.

## Alerts

A rule is a trigger, a condition, and a channel. Rules run in-process after the write that could fire them. There is no queue.

| Part | Options |
|---|---|
| Trigger | `run.completed`, `score.written`, `disagreement.created`, `judge.calibrated` |
| Condition | `{score, aggregate: 'mean' \| 'min' \| 'count_below', operator, threshold, scope: 'run' \| 'trace' \| 'window', window_n?, min_n?}` and optional `filters` on metadata |
| Channel | `webhook` (JSON POST, `X-Spotter-Signature` HMAC, retries 3), `slack` (incoming webhook URL, block template), `email` (SMTP from `SPOTTER_SMTP_URL`, text template) |
| Controls | `enabled`, `cooldown_s` per rule, a Test button that sends a sample payload, a delivery log with status and response |

Every payload includes the rule name, the numbers that tripped it, and deep links to the run, the compare view against the previous run, and the failing traces. Templates are Mustache over the same payload, so a Slack message and an email differ only in the template. Deep link `/alerts` and `/alerts/{id}/deliveries`.

## Datasets from traces

Datasets are how error analysis turns into a permanent test.

- `POST /datasets/{id}/items/from-traces {trace_ids, expected_from: 'human' \| 'output' \| null, tags?}` copies traces into items with `source_trace_id` set. `human` takes `expected` from the human verdict and note; `output` takes the trace output as the new reference; `null` leaves it for later.
- In review, `A` adds the current trace to a dataset chosen from a picker; in compare and the trace list, a selection can be added in bulk.
- A dataset with `purpose: judge_labels` holds items whose `expected` is a human verdict. `spotter judge run <name> --version N --dataset <id>` scores those items and writes a calibration for that version against that dataset. This is how a judge is tested before it is activated.
- Items are never deleted; `archived_at` hides them. Runs record `item_count` and `items_hash` so a run stays comparable to earlier runs after items are added.
- Deep links: `/datasets/{id}/items?tag=transfer`, `/datasets/{id}/items/{item_id}` (item with its source trace and every run's output).

## Judge versioning

A judge is a name with an immutable version history and one active version.

- **Auto-versioning.** Any change to `prompt`, `model`, `params`, or `examples` creates a new `judge_version` with `number = max + 1` and `parent_id` pointing at the version it was derived from. `content_hash` is the SHA-256 of those four fields; a proposal whose hash already exists returns the existing version instead of creating one.
- **Immutability.** Versions are never updated or deleted. Every judge score records `judge_version_id`, so any aggregate can be recomputed for any version.
- **Active version.** `judge.active_version_id` is the only mutable field. Activating an older version is the rollback. The SDK and CLI resolve `--version active` to it by default.
- **Human verdict on the judge.** A human score on a trace with the same `name` as a judge score is the ground truth for that trace. A disagreement is a trace where `human.value != judge.value` for the same name and version. Calibration for a version is computed from these pairs on the dev and test splits.
- **Where judges run.** The server stores definitions and results; it never calls a model. `spotter judge run <name> --version N --run <run_id>` fetches the version definition, calls the model, and writes scores tagged with the version. An agent can do the same through the SDK.

MCP operations for the loop:

| Call | Effect |
|---|---|
| `read {type: "judge", id: name}` | Versions with calibration per version, the active marker, and `url` |
| `list {type: "disagreements", judge, version}` | Traces where human and judge differ, each with `url` |
| `write {op: "judge.propose", judge, from_version, prompt?, model?, params?, examples?, note}` | New inactive version, or the existing one if the hash matches |
| `write {op: "judge.activate", judge, version}` | Sets the active version; the previous active is recorded in `note` for the audit trail |

Deep links: `/judges/{name}` (timeline), `/judges/{name}/versions/{n}` (definition and calibration), `/judges/{name}/disagreements?version={n}` (review queue filtered to the disagreements, so a person can re-label or confirm).

## MCP tools

Four tools over the same API, added after the CLI works.

| Tool | Purpose |
|---|---|
| `list` | Datasets, items, runs, traces, judges, disagreements, alerts, deliveries with filters |
| `read` | One run with aggregates, or one trace with spans and scores in a single call |
| `write` | Scores (with `turn`), traces, trace metadata patches, runs, items from traces, judge versions, judge activation, alert rules; validates against a schema first |
| `compare` | The pivoted compare table for two or more runs |

Every result carries a URL into the UI.

## OTLP ingestion

`POST /otel/v1/traces` accepts OTLP/HTTP JSON and protobuf. One OTel trace becomes one Spotter trace: `gen_ai.*` message attributes fill `messages`, token attributes fill `metrics`, spans are kept under `spans`, every other attribute is kept raw under `metadata.attributes`, span events become `events`, and the project's `attribute_map` promotes the chosen ones. A trace that arrives in several batches is merged by trace id.

## Non-goals

Prompt management for the task under test (git owns those prompts), playgrounds, dashboards, multi-user access control, server-side code or model execution.
