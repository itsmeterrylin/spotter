# Copper Evaluations: system design

**Status**: Draft, 2026-09-06
**Scope**: A local, single-user tool for running and comparing LLM evaluations, with a human review loop and calibrated LLM judges.

## Goal

Run a test set through an LLM task, score every result, compare two runs by test case, and keep humans in the loop until the automated judge agrees with them.

## Principles

1. **The server never runs the task.** The SDK runs the task and the scorers and posts results. The server stores, aggregates, and compares.
2. **Binary verdicts.** A score is a name and a number. Human review is Pass or Fail with a note. No 1 to 5 scales.
3. **Error analysis before judges.** Read traces, write notes, group notes into failure modes, then write one judge per failure mode.
4. **Judges are validated, not trusted.** Every LLM judge is measured against human labels before its output counts.
5. **One process, one file.** SQLite and a single Python service. No containers.

## Data model

Six tables. A trace with a `run_id` is an experiment result. A trace without one is a production log.

| Table | Columns |
|---|---|
| `project` | `id`, `name` |
| `dataset` | `id`, `project_id`, `name`, `description` |
| `dataset_item` | `id` (client-set), `dataset_id`, `input` JSON, `expected` JSON, `metadata` JSON |
| `run` | `id`, `dataset_id`, `name`, `metadata` JSON (model, prompt version, git sha), `started_at`, `ended_at` |
| `trace` | `id` (client-set), `project_id`, `run_id` nullable, `dataset_item_id` nullable, `input`, `output`, `expected`, `metadata`, `tags`, `start`, `end`, `metrics` JSON (`prompt_tokens`, `completion_tokens`, `duration_ms`, `errors`), `spans` JSON nullable |
| `score` | `id`, `trace_id`, `name`, `value` REAL, `label` nullable, `reason` nullable, `source` (`sdk`, `judge`, `human`) |

Relationship chain:

```
dataset ──< dataset_item ──< trace >── run
                                │
                              score
```

Run aggregates (mean per score name, p50 duration, tokens) are computed on read, never stored.

Ids are UUIDv7, generated by the client, so scores can be written before the server acknowledges the trace.

## API

| Method | Path | Purpose |
|---|---|---|
| POST | `/datasets` | Create dataset |
| PUT | `/datasets/{id}/items` | Upsert items by client id |
| POST | `/runs` | Create run |
| POST | `/traces/batch` | Insert traces; rows may carry `run_id`, `dataset_item_id`, `scores[]` |
| PUT | `/traces/{id}/scores` | Add or replace scores on a trace |
| GET | `/runs/{id}` | Run with aggregates |
| GET | `/runs/{id}/summary?compare_to=` | Per score name: mean, diff, improvements, regressions |
| GET | `/datasets/{id}/compare?run_ids=` | Items with nested per-run output and scores |
| GET | `/traces?filters=` | Filter grammar `[{field, key, operator, value}]` with symbol operators |
| POST | `/query` | Read-only SQL over the tables |

Filter operators: `=`, `!=`, `<`, `<=`, `>`, `>=`, `contains`, `starts_with`, `in`, `is_empty`.

## SDK and CLI

```python
from copper_evals import Eval

def task(item):
    return my_pipeline(item.input["transcript"])

def exercise_match(item, output):
    return {"name": "exercise_match", "value": float(output["exercise"] == item.expected["exercise"])}

Eval("tagging-golden", task=task, scores=[exercise_match], metadata={"model": "rules-v1"})
```

```
copper-evals run evals/tagging.py            # runs, posts, prints the summary table
copper-evals run evals/tagging.py --no-send  # prints only
copper-evals compare <run_a> <run_b>         # summary with diffs
```

The summary table shows each score name with mean, diff versus the previous run, improvements, and regressions.

## Review interface

One screen, one trace at a time.

- Input, output, and expected in their native format. Markdown rendered, JSON collapsible, transcripts as transcripts.
- Pass, Fail, Defer as large buttons. Keys `1`, `2`, `D`. Undo with `U`.
- One notes field. Auto-save on every action.
- Counter: position, remaining, labeled.
- Failure tags appear only after error analysis has produced a taxonomy.
- Traces are loaded from a sample file. Sampling stays outside the app.

## Judge validation

1. Collect about 100 human labels per failure mode, balanced between Pass and Fail.
2. Split 15% train (few-shot examples), 45% dev, 40% test.
3. Measure true positive rate and true negative rate on dev. Iterate the prompt until both exceed 90%.
4. Run once on test. Record TPR and TNR with the judge version.
5. Report production pass rates corrected for judge error, with a bootstrapped confidence interval.

A judge whose TPR or TNR is unknown shows as `pending` in the UI and its scores do not enter run aggregates.

## MCP tools

Four tools over the same API, added after the CLI works.

| Tool | Purpose |
|---|---|
| `list` | Datasets, runs, traces with filters |
| `read` | One run with aggregates, or one trace with spans and scores in a single call |
| `write` | Scores, traces, runs; validates against a schema first |
| `compare` | The pivoted compare table for two or more runs |

Every result carries a URL into the UI.
